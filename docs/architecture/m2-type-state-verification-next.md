# Next: type-state verification contract

Status: proposed direction after the bounded Code-validation approval on 2026-11-04. Exact-contract planning is authorized; production implementation is not. The technical director must settle inputs, identity services, algorithms, version policy, limits, result guarantees and acceptance tests before worker dispatch. No NanoSpec and no new user approval are required for this already-authorized direction.

The next objective is a coherent Java SE 21 method type checker, covering the instruction set independently of interpreter execution support. Do not spend another increment extending representation checks while describing them as verification. Reuse the accepted whole-Code foundation and preserve its independent API. The two original dead-code type failures currently accepted by that service should become negative evidence for the new checker.

The normative basis is [JVMS 4.10.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.10.1). It defines verification types, stack-map transitions, initial method frames, protected-member checks and instruction rules. Constructor state includes an initialization flag; exceptional constructor edges differ from normal completion. Full class verification also has obligations outside Code. Historical inference and the optional version-50 fallback require a separate declared policy. The next contract must inventory those rules and distinguish a checked method from a fully verified class.

Plan the complete modern method proof: category-two locals and overlapping stores, operand stack manipulation, branch/handler states, required frames, unreachable blocks with supplied maps, stack capacities, return and fall-off rules, arrays and all invocation forms. Constructors need exact new-offset and uninitializedThis identities, alias substitution, before-chain own-field constraints, handler states and designated Object treatment. The runtime's dynamic allocation keys and successful execution paths are not substitutes for the verifier's symbolic proof.

Resolve reference and protected-member prerequisites explicitly. Verification needs an immutable, loader-aware view of relevant class facts, with precise ownership of class loading and callback failures. Do not silently use names as identities, trust an arbitrary host boolean as proof, initialize classes during verification, or reuse runtime assignment/selection rules without checking their suitability for verification. Choose a dependency boundary that preserves classfile/decoder independence. The exact contract must say which facts are trusted inputs, which are validated, and which unresolved dependencies yield a structured unsupported or host failure rather than successful verification.

Use a result whose lifetime or identity fingerprint binds the inspected metadata and required environment. Full-class readiness must later aggregate all method and non-Code obligations; a single method result cannot stand in for it. Existing body/session entry points remain unchanged until a separately reviewed integration gate specifies error ordering and cache invalidation. No fabricated VerifyError objects or implicit launch capability should accompany the library API.

Bound the actual verification algorithm. Specify limits for retained types/states, frame expansion, transitions, exception edges, descriptor work, hierarchy queries and any worklist or cache. Compressed maps and overlapping handlers must not amplify work without a charge; recursive class graphs and method control flow must use bounded iterative processing. Fund allocations before publication and keep source metadata immutable. State exactly whether caches retain compact symbols or resolved identities, and prevent copied long descriptors or full frame histories from defeating the limits.

Keep independent acceptance evidence. The coordinator should extend stage-aware original encodings with valid and invalid stack/local transitions, missing or inconsistent frames, constructor normal/exception paths, protected receivers, arrays, loader distinctions and resource boundaries. Use genuine complete methods beyond the executable opcode subset. Distinguish format, verification, loading/linking and execution failures; retain the reference JDK only in tooling. Workers should independently test every modern opcode rule and adversarial graph/state sizes. A fresh-target combined gate and frozen source review remain mandatory.

If a necessary class-fact service must precede the checker, justify that prerequisite with concrete API dependencies and retain the complete checker as the immediate objective. Unsupported historical inference, whole-class checks or loading obligations must remain named open work, not be hidden behind a universal VerifiedClass label. Full M2, JVM conformance and demonstrated performance superiority remain joint long-term requirements.
