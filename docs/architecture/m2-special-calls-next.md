# Next ordinary special-call increment

Status: superseded by the implemented and approved contract `m2-special-calls.md` on 2026-11-04; final evidence is in `m2-special-calls-review.md`. The rationale below is retained as history. The proposed subsequent direction is `m2-reference-types-next.md`.

The next coherent execution increment should add ordinary nonconstructor invokespecial to the existing runtime-aware numeric/void body engine. It enables explicit superclass calls and direct-superinterface default calls that ordinary Java code emits. Same-class/interface private calls can reuse the service where the encoding is legal. This complements virtual/interface dispatch without pretending that allocated storage has passed a constructor or that class initialization is implemented.

The likely public addition is `FieldResolutionContext::select_special(origin, index, receiver) -> Result<MethodId, MethodAccessError>`, preserving the existing host entry point and shared engine. Final API details remain a contract task. Reuse symbolic resolution, accessibility, explicit Object metadata, admitted identity graph and maximally-specific candidate analysis. Special selection needs its own lookup origin; calling select_virtual/select_interface and accepting their receiver-directed target would be incorrect.

Under [JVMS invokespecial](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.invokespecial), ordinary superclass calls can begin selection at the current class's direct superclass even when the symbolic reference names an older ancestor. Selection then searches instance declarations from that prescribed type, followed by the specified Object/interface fallback. The actual receiver's override must not intercept a super call. Resolve access/staticness first; null and selected abstract/default-conflict handling retain their specified order. The final contract must distinguish the resolved declaration, selection start type and selected body in both code and diagnostics.

Two format/verification details need explicit defenses. First, the Java SE 21 runtime treats ACC_SUPER as set even for old files that omit the bit; do not gate modern special selection on its raw stored value. Second, accepted symbolic owners and receiver relationships require checks appropriate to nonconstructor calls, including current type, superclass, direct superinterface and Object cases. Interface references before major 52 must be rejected. Use [JVMS 4.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.1), [4.9.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.9.1) and [4.9.2](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.9.2) when pinning these checks. Invalid structural receiver/owner relationships should remain checked host failures until a verifier establishes them, rather than invented linkage outcomes.

Keep `<init>` and `<clinit>` explicitly unsupported in the new path. Constructor support requires a separate uninitialized-reference protocol: allocation-site identities, alias transitions, constructor delegation, exceptional exits and verifier constraints. A memory-service instance handle must not be relabeled as successfully constructed merely because one ordinary method executes. Likewise, keep native/synchronized/handler exclusions and existing reference-descriptor/nest/module boundaries. General static invocation and lifecycle responsibilities are separate work.

The implementation should add one call discriminator and use the same resolved-instance preparation, MethodId cache, per-frame CP/origin, typed arguments and return transfer. Cache eligibility must remain checked when the same method is reached through virtual, interface, special or static paths. Count prepared bytes once per MethodId, keep cumulative context work charged before traversal, and preserve all heap effects and diagnostic transition sites after failures. Do not duplicate the engine or hierarchy.

Acceptance should include genuine superclass overrides, calls naming an ancestor beyond the direct parent, private calls in legal historical encodings, explicit interface-super defaults, inherited defaults through a superclass, class/interface bodies alternating invocation forms, hidden-field effects, mixed numeric/void values and failure persistence. Synthetic coverage should isolate raw ACC_SUPER absence, old-version InterfaceMethodref rejection, indirect-superinterface/unrelated-owner rejection, wrong receiver identity, static/null/abstract/conflict precedence, exact budgets and same-MethodId cache reuse. Genuine outputs remain JDK development-time oracles; malformed-host-policy cases are tested separately.

After ordinary special calls, the roadmap still needs reference assignability/values, object and exception protocols, lifecycle initialization, verification, library/native integration, monitors and collection. This note does not assert that finishing invocation opcodes completes M2 or Java SE 21 conformance.
