# Next: Throwable identity and exception propagation

Status: historical direction, superseded by the exact `m2-exception-dispatch.md` contract and its approved `m2-exception-dispatch-review.md` implementation on 2026-11-04. The questions below document the design inputs; they are not additional implementation authorization. Full M2 remains open.

The body engine now carries ordinary references through calls and returns. The next coherent direction is explicit throwing, handler selection and abrupt frame completion. These are prerequisites for useful catch/finally behavior and later constructor/class-initializer failures. Preserve the current engine and actual heap identities; do not bolt on a separate exception interpreter or treat a symbolic outcome tag as a Throwable object.

An exception has a Throwable-compatible instance identity. Handler lookup preserves table order and the throwing instruction's protected range. A successful handler resumes with the thrown reference as the sole operand-stack item; unwinding discards intervening frames. See [JVMS exceptions](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.10) and [athrow](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.athrow).

The exact contract must settle these dependencies before enabling Code exception tables:

- Explicit Throwable identity must be bound to admitted registry/loader/heap metadata. Reuse the existing universe, class relation and handle checks without granting identity by name alone. Reject arrays and unrelated instances as host validation failures; null athrow needs an explicit NullPointerException production policy.
- Define how each currently supported synchronous Java outcome obtains a real checked exception reference, including allocation/state/resource limits. Existing symbolic outcomes cannot silently bypass a newly enabled handler. No default-only allocation may be described as successful Java exception construction or initialized Throwable library state. If lawful materialization is outside the first bounded profile, expose that limitation as a distinct host failure before pretending a catch or uncaught Java completion occurred.
- Distinguish already supplied Throwable references from VM-produced exceptions. Throwing/rethrowing a supplied instance must preserve its identity. Specify host-visible uncaught-reference results and retain the older entry-point contracts explicitly. Host policy/invalid-input errors remain host failures and are never intercepted by Java handlers.
- Validate handler ranges/targets against decoded instruction boundaries, then resolve typed catches using the current declaring loader and required access/loading rules. Catch-all entries, typed order, lazy/eager resolution policy and failures during catch resolution need precise precedence. Structural checks are not a substitute for full bytecode verification.
- Use the actual throwing PC in the current frame and the invocation PC when searching a caller after unwind, rather than its already advanced resume PC. Preserve locals, clear the receiving operand stack, release unwound slot reservations and keep earlier heap effects. Bound matching, resolution and unwind work with existing policies or a justified explicit extension; keep all traversal iterative.

A useful first executable slice should exercise supplied exception references through explicit athrow, same-frame and cross-frame catches, rethrow and catch-all cleanup, plus every VM-produced outcome whose materialization contract is actually implemented. It must fail explicitly for any unsupported throwable production rather than produce fabricated objects or skip matching handlers. Native/synchronized methods, monitor release, asynchronous exceptions, messages/stack traces, construction/initialization and collection remain separate obligations unless deliberately included with evidence.

The runtime worker should own Throwable identity validation, catch-type resolution and the chosen bounded production service. The interpreter worker should own prepared handler metadata, athrow, the single shared unwind path and diagnostics. Root should supply original JDK fixtures and independent numeric/identity/state observations. Cases should cover overlapping ranges and first-match order, valid Throwable superclass catches and invalid interface/unrelated catch types, exact range endpoints, caller invocation PCs, locals/operand clearing, nested finally/rethrow, identity and aliases, deep unwind, null/foreign/stale/unrelated throws, resolution failures, all budgets and preserved effects. No implementation may start merely because this direction note exists.
