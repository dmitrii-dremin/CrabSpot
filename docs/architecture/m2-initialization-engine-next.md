# Next: initialization scheduling and failure protocol

Status: historical proposal fulfilled by the bounded contract `m2-initialization-session.md` and its approved implementation review `m2-initialization-session-review.md` on 2026-11-04. The proposal below records the design questions that led to that increment; the exact contract governs implemented APIs and responsibilities. Full M2 and complete linking/initialization remain open.

Checked static locations and supplied-Throwable dispatch now provide the storage and abrupt-completion mechanisms for actual initializer execution. The next useful increment should establish a bounded initialization scheduler over explicitly admitted metadata, with real clinit bodies executed through the same engine. Preserve the existing host-controlled body profiles; do not silently turn their static reads/writes into initialization triggers.

The exact contract must distinguish prerequisites from execution state. Registry admission and static allocation are not verification or complete preparation. Define what the bounded profile validates, which unresolved linking/loading obligations remain unsupported, and how identities associate initialization state with the actual declaring ClassId. No host setter may certify success for skipped code. Initialization ordering, recursion and failure requirements come from [JVMS 5.5](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.5).

Pin these points before dispatch:

- A private initialization state machine with explicit execution ownership, dependency scheduling and exactly-once successful completion. Separate same-execution recursive use from a concurrent or conflicting request. The current single-engine profile cannot claim thread synchronization or Java Memory Model initialization guarantees.
- Supported ConstantValue installation at the required stage and tightly scoped final-write authority for actual declaring initializer frames. Numeric constants can form a bounded first slice; unsupported String/interner prerequisites must fail explicitly before a false successful transition. General final writes stay forbidden.
- Dependency order for class superclasses and relevant default-method interfaces, and the distinct interface rules. Reuse admitted identities; do not infer bootstrap classes by names or initialize every interface indiscriminately. Traversal and scheduling must be iterative and bounded.
- A new opt-in active-use boundary identifying the resolved declaration, scheduling needed initialization, then resuming the original access/call without double execution or lost operands. Reuse the MethodId cache, static/reference services and exception engine. Do not broaden ordinary static resolution or constructors accidentally through a special initializer path.
- A complete policy for normal completion, supplied Error propagation, non-Error wrapping requirements, later erroneous-class use and unsupported VM-produced failures. ExceptionInInitializerError and NoClassDefFoundError objects do not yet exist. Either provide lawful materialization within an explicit reviewed scope or return a distinct unsupported host result; a symbolic tag or default-filled instance cannot stand in for a constructed Throwable.
- Host fuel, memory or resolver interruption after partial static/heap effects. Such interruption must not be confused with Java abrupt completion, successful initialization or safe automatic retry. Define retained ownership/state and subsequent-call behavior explicitly. No hidden rollback of already executed Java effects and no stranded in-progress state may escape the contract.
- Immutable metadata borrowing, bounded initialization records/dependency work, cache accounting, stack/fuel sharing and exact failure precedence. Initialization records and static-memory extension need compatible snapshot/growth rules.

Root should supply original JDK cases for constants, superclass/default-interface order, once-only execution, recursive cycles, actual clinit effects and failures only where the new profile implements the corresponding behavior. Independent trace/state assertions must distinguish the class that declares a field from a symbolic subclass. Synthetic cases should cover unsupported prerequisites, final-write authority, reentry/ownership, dependency limits, host interruption, retained effects and subsequent requests. Retain all existing oracle/profile behavior.

Runtime ownership should cover initialization identities, state transitions, prerequisite/constant validation and scheduling decisions. Interpreter ownership should cover actual initializer frames, suspension/resumption of triggering actions and precise abrupt completion. Root owns fixtures and the independent gate. Constructor uninitialized-value tracking, full library bootstrap, VM exception construction outside the chosen profile, multithreaded initialization and Java application startup remain separate obligations.
