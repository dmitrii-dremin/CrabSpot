# Next proposal for a verified application entry

**Proposed for exact-contract planning after member-resolution acceptance.** Run an original `public static void main(String[])` from a directory of Java 21 class files. The user supplies an application class and a bounded platform-class source. CrabSpot supplies the loader identities, verifies the classes, prepares storage, constructs a real empty argument array and runs main. Today a test author performs these steps and supplies the ClassIds, hierarchy plans, binding facts and runtime profiles manually. Closing that gap would exercise the existing VM through its normal launcher.

## One owner for the run

Add a library coordinator to the existing launcher crate and keep its CLI thin. The launcher may depend on runtime, verifier and interpreter. The parser and verifier keep their filesystem-independent APIs. Use a fresh, single-threaded execution image per run, with one bootstrap namespace, one application loader and deterministic parent-first delegation. The first contract should choose bounded, explicitly enumerated directory inputs. Cap entries, class bytes, total input bytes and name lengths before growth. Use the opened bytes as the sole source of each immutable definition. Specify path/name agreement, duplicate definitions, deterministic enumeration and directory containment. Keep Java class files from JARs, arbitrary class-loader code and concurrent or mid-execution domain growth for later increments.

The image owns its LoadingDomain, actual initiation records, plans, heap and per-class phase records. Route successful source requests through checked domain definition or delegation. Build hierarchy and verifier binding facts from the same recorded identities. An equality constraint or a CP spelling alone cannot stand in for a successful load. Define a deliberate closed-input policy and its observable failure order. For example, an explicitly admitted image may reject an invalid unused application class before entry, whereas a JVM with lazy linking may never request it. Label that as an image-preflight outcome in reference evidence.

Verify every class permitted to execute before publishing execution authority. Bind that authority to the exact domain, initiating graph, version/preview policy and admitted ClassIds. A private staged coordinator can run the existing borrowed class proofs, consume their results, then release the immutable verifier environment before mutably borrowing the same domain to prepare and execute. Seal the input graph against subsequent mutation. A host cannot attach a success flag to a different registry or introduce an unverified target through virtual dispatch, an initializer or a constructor. Maintain separate records for verification result, preparation witness, CP resolution and the existing initialization-session state. Keep the session within a lexical borrow of its owner so the image requires no self-referential Rust struct.

Use genuine platform class bytes for the acceptance run, including the designated Object, String, Throwable, Error and verifier-core roles. An extracted, bounded Java 21 platform directory is a feasible source: the existing java.base harness already reads, defines and verifies a real corpus. A reference tool may prepare that input outside the VM. The launcher itself must never ask a reference VM to load or execute application code. The exact contract should choose between verifying the full supplied boot image once and admitting a smaller proved executable subset. Additional read-only hierarchy facts must have explicit provenance and cannot become executable without proof. Limit application-to-platform access to a declared supported bootstrap surface until module access facts are implemented. Avoid a general trust exemption for platform packages.

## Observable entry and failure

Select the actual public static main with descriptor `([Ljava/lang/String;)V` using a pinned launcher lookup policy. Construct a non-null length-zero reference array whose component is the designated bootstrap String ClassId, even when the application CP has no separate Class entry naming String. Existing heap allocation quotas and checks apply. Run through the same checked member context, static state and InitializationSession. A typed host library result can expose the final return or supplied uncaught exception and a bounded, read-only observation of application static state for testing. Start with zero command-line arguments. Java String creation, standard streams, System.exit and broad native-library support need separate implementations.

Keep source I/O, malformed bytes, missing prerequisite facts, resource exhaustion, Java verification/linkage failures, initialization failures and user-code outcomes distinguishable. Pin which failure category is stable and what earlier work survives. A true failed Java resolution and a temporary source/host prerequisite need different treatment. An exact first contract can use one image-construction attempt and one run, so failing image admission cannot transfer a partly verified image to execution. Full lazy Class CP failure persistence, loader callbacks during frames and reopening failed images remain explicit future work. [JVMS 5.2](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.2), [5.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.3), [5.4](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4) and [5.5](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.5).

## First acceptance scenario

Compile a small original program with a main class, helper, interface and two implementations. Its main checks the empty argument array, allocates an implementation, calls it through the interface, invokes a static helper and records an integer result and initialization count in application fields. Check the ordinary launcher entry and those values against independent JDK runs. The Rust test supplies directory paths and the entry name only. A second class with a well-formed but type-invalid method must fail verification before its initializer can change a sentinel or main can run. Add duplicate or wrong-name inputs, a missing hierarchy dependency, missing/incorrect main, unsupported platform access, a loader-name collision and exceptional completion after an observable write. Report the stage on each VM and separate image-policy differences from Java failures.

The implementation split is practical: one worker builds bounded source admission, identity routing and sealed proof/preparation ownership; the other implements the CLI/entry-array/engine adapter and independent adversarial tests against an immutable API snapshot. The coordinator owns original sources, JDK fixtures and end-to-end evidence. The exact contract must specify quotas for an entire image and define the lifecycle/error table before either worker starts. Milestone approval for application execution, Java SE compatibility and performance remains open.
