# Execute distinct-string equality through the supplied Java library

**Proposed next increment following the String length/body gate.** Support the complete matched `String.equals(Object)` path on kernel Strings, including byte comparisons between distinct objects of either coder. This adds a common operation on application arguments without requiring another Java exception producer, endian native or general ClassLoader representation. The reusable prerequisite is the matched bootstrap assertion-status path for system-class mirrors. Freeze a separate contract only after the current body profile passes its gate.

### What the application actually exercises

An original nine-argument program makes ten calls through one `invokevirtual java/lang/Object.equals:(Ljava/lang/Object;)Z` at bytecode 10 of a helper. Its application-side types need only Object and String. The external driver creates fresh Strings with exact units, including NUL and an isolated low surrogate, and never joins the execution image. Zulu 21.0.7 in default and noncompact modes and pinned Semeru OpenJ9 21.0.13 all returned `511/10`. The compiled application SHA-256 is `4D298359C301DE121E3CFFE694BD28217C01778F2F7EF54D6508B06F9A3D7E64`. The cases include identical object, null, non-String, distinct equal Latin and wide objects, equal empties, last-unit differences, mixed coders and different lengths. Controlled public UTF-16 inputs reproduce all nine positions. A separate CLI case must use OS-transportable values. Compare actual receiver selection, retained flags and call counts, not just an exit status. This is reference-only planning evidence.

The captured Zulu String returns immediately for identical references at PC 6 and tests the argument class at PC 8. Only two distinct Strings reach the active field read COMPACT_STRINGS at PC 19. The body compares the actual coder bytes, loads both actual backing arrays and calls static StringLatin1.equals([B[B)Z at PC 44, even for two wide Strings. The helper checks both lengths, executes two baload operations per compared byte and can return at the first difference. An alias check does not establish support for distinct Strings. OpenJ9's captured equals body instead calls lengthInternal at PCs 22 and 28, then compares backing references before its own implementation path. Its result is an independent reference, with separate implementation support required. [Java 21 String.equals](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/String.html#equals(java.lang.Object))

### Acceptance and subsequent charAt work

**Assertion and loader controls.** Twenty independent Java processes ran ten option sets on each of the pinned Zulu and OpenJ9 builds. Each process ran the two status guests, completed the equality application and then inspected the library fields. All returned `511/10`. A bootstrap-only guest separately calls String.class.desiredAssertionStatus and Object.class.desiredAssertionStatus. A second guest compares the public desired status of its own class with the side effect of an actual Java assert statement. The observer and its two independently defined loader copies remain outside the guest image. Exact commands, class/source hashes, versions and outputs are retained in `equality-probe/policy-rows.json`, private evidence SHA-256 `1BFC6409A3020872A82834C4DFC92F2789C0F8ABAFA52C2DEEAD0958405F95FF`.

* Default and -dsa yielded false for the two bootstrap classes, the application and the helper. With -ea, both VMs enabled the app assertion while the bootstrap classes stayed disabled. With -esa, both enabled desired status for String, Object and StringLatin1 and kept the app off. Under -esa -da:java.lang.StringLatin1, the other two system classes remained enabled and the helper's desired status became false. Running -esa -dsa restored default results. The isolated -ea:app.Policy, -ea:java.lang.StringLatin1, -ea -esa, and -ea -esa -da:app.Policy cases additionally discriminate named and system choices.
* Under -esa, Zulu reported the genuine StringLatin1 assertions-disabled field as false and OpenJ9 as true, despite both reporting the helper's current desired status as true. The two actual helper classfiles both invert the query during initialization. The records establish post-startup field values and current query results, not when the helper first initialized in either VM. Do not hard-code OpenJ9's field report or require two vendors to have had the same bootstrap timeline. Zulu reports desired status false for all three tested arrays under -esa. OpenJ9 returned true/false/true for String[], application array and int[]. Unsupported array/app-loader queries must stay explicit in the proposed bootstrap-only production profile.
* Two fresh defining loaders used identical app.Policy bytes. One initialized with assertions enabled then switched its desired class setting to disabled. Its actual assert body ran both times although the later public query became false. The reverse switch returned true from the later query but never ran the assert body. Both VMs gave these results. Distinguish a frozen initialization-time class effect from later ClassLoader policy; bootstrap-null behavior cannot stand in for the nonnull application-loader branch.
* The Zulu observer found actual zero-length Class[] and ObjectStreamField[] in Class's private static fields after startup. On OpenJ9 those field names were absent from reflection; its Class initializer instead uses EmptyParameters, and desiredAssertionStatus begins by invoking getClassLoaderImpl. For CrabSpot, use exact original Class Code and typed identity/length inspection after a successful run. At one-short array capacity, require the first static write to survive and the later write to remain unset. At one-short Code/frame/fuel, require the actual Class or StringLatin1 location and caller, registered-role state, and retained application fields. Use a nondefault bootstrap assertion policy to require an observable native result change while equality still returns exactly the same bits. Test an incorrect or unregistered native role for an explicit failure; a no-op bootstrap hook or constant answer must fail these controls.

Require physical CLI and public API evidence, lowered fuel at the genuine byte loop, and separate role/lifecycle evidence. Alias/null/non-String cases should return without touching the helper; mixed-coder rejection can initialize String and issue backings without initializing StringLatin1. Equal same-coder distinct operands must enter StringLatin1, initialize it and Class through regular frames, observe its assertions-disabled flag, and expose stable canonical mirror/array identities.
