# Next proposal for loader constraints during preparation

The next contract should give CrabSpot a persistent way to record what a loader has initiated and which loaders must agree on a named class. The class verifier already proves every declaration against an immutable set of known identities. The runtime still needs to enforce agreements made before a particular name has resolved, including when either loader obtains its identity later. The installed java.base run uses one bootstrap loader. Cross-loader enforcement needs its own evidence.

## Proposed increment

1. Specify one registry-bound runtime service for initiating-loader records and per-name equivalence classes. It must handle a constraint imposed before either identity exists, after one binding, and after both. Compare canonical ClassIds. A failed insertion retracts the attempted relation or binding and keeps previous obligations effective. The contract should distinguish a defining-loader entry from another loader initiating that same class through delegation. Resolve the ownership boundary with the existing definition and lookup APIs, so a later definition cannot bypass an active checked loader state. [JVMS 5.3.2 and 5.3.4](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.3.4).
2. Define a checked source of constraints during preparation. Cover both a declared method overriding an ancestor method and a superinterface method whose implementation is inherited. Use the defining loaders of the actual declarations required by each rule. Handle package-transitive overriding, defaults, abstract candidates, static/private exclusions, and repeated nominal types in signatures. Array descriptors contribute their ultimate nominal element where applicable. Record obligations without forcing unrelated classes to load. [JVMS 5.4.2](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.2), [5.4.5](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.5) and [5.4.6](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.6).
3. Pin deterministic declaration and constraint order, including the first failing constraint in a multi-constraint operation. Define which earlier, successfully imposed constraints survive. Bound retained names, loader/name pairs, relations, descriptor scans, hierarchy traversal and transitive lookup work. Test retraction against allocation and budget failures as well as actual identity disagreement. A symbolic Java linkage failure and host resource exhaustion require distinct diagnostics.
4. Require fresh-loader JDK reference cases with stage-aware outcomes. Include two distinct definitions of the same name, independent names that may differ, legal common delegation, conflicting existing identities, a later conflicting load, and a three-loader transitive conflict. Include an inherited implementation whose declaring loader differs from the prepared class's loader, plus multidimensional reference and primitive array signatures. Expose separating original bytecodes, loader topology and observed failure stages in provenance. Synthetic tests can check internal accounting and exact preservation of existing constraints after failures.

This proposal authorizes exact-contract planning after class-proof acceptance. Its first checkpoint should settle how the existing registry, immutable verifier environment and mutable loading state share identity and lifetime without invalidating prior evidence. Resolution-time field/method constraints, verification failure caching, complete module access, historical inference, and a checked execution entry point need subsequent contracts. Publishing this service alone would establish only the loading and preparation rules it actually implements.
