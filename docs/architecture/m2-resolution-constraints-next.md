# Next proposal for checked member resolution during execution

**Proposed for exact-contract planning after preparation-constraint acceptance.** The next milestone should run an original Java caller that accesses a reference field and invokes a method across defining loaders. Today the runtime can execute these instructions and can independently enforce loader agreements during preparation, but the field and method resolution paths still reject cross-loader nominal descriptors outright. A legal common delegation should enable the call. A split binding should fail at the first resolution that uses it. This gives the next contract a concrete application outcome.

## Ownership and operation

Bring one opt-in execution context into the existing interpreter engine. It must use immutable canonical registry metadata, a heap/layout snapshot, actual initiating records and the mutable constraint ledger from the same LoadingDomain. The current LoadingContext borrows the entire domain mutably; the existing FieldResolutionContext borrows its registry. The design must split these authorities safely, keep the ledger private, and preclude retaining a resolver result from an unrelated loader topology. Pin what an unresolved ordinary name means in a context restricted to already admitted definitions. Give callers a way to define or delegate that name and retry a genuine *host-prerequisite* failure after the active borrow ends. Retain the conservative checks for entry points without domain authority.

Resolve each ordinary Fieldref, Methodref and InterfaceMethodref from the defining loader of its owning class. After the prescribed access checks impose signature-leaf agreements against the **resolved declaring loader**, including an inherited member reached through a different symbolic owner. A dynamically selected override is a separate identity. Keep resolution, instruction-specific checks, selection, checked value transfer and active-use initialization in their proper order. Cover ordinary fields and the already executed invocation forms, accounting explicitly for constructor owner checks, special-super selection and nominal signatures in inherited/default methods. Probe partial multi-leaf failures before selecting their deterministic order. [JVMS 5.4.3.2](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3.2), [5.4.3.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3.3) and [5.4.3.4](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3.4).

The contract must settle persistent CP-site identity, successful resolution reuse, and repeated Java linkage failures. A symbolic member can be successfully resolved even if a particular invocation subsequently fails an opcode-category or receiver check. A resource or missing-host-metadata failure needs its own retry semantics. Specify which information can be cached symbolically under the existing exception materialization boundary, and limit claims about actual Throwable identity accordingly. Bound the site table, signature and loader work, once-only publication and recovery. An access failure may involve nest, protected or module facts outside the current profile. Keep those boundaries explicit. [JVMS 5.4.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3) and [5.4.4](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.4).

The existing method-value path conservatively audits matching declarations across the receiver's hierarchy. The contract must define what establishes the selected receiver's **preparation constraints** before relaxing that guard. Accept immutable compatible preparation evidence, or have the new checked execution path impose the required preparation obligations on the actual owners before selection. An equality between caller and resolved declarer alone cannot establish all those agreements. Equally, a successfully checked class type proof certifies its own method bodies and frozen verification facts; it does not record preparation or make arbitrary runtime bindings equivalent. Keep this evidence and the initialization session's execution state separate.

## Required outcome

Run a genuine numeric Java entry method through the existing engine with three defining loaders, a nominal argument/result, and a field inherited through a different symbolic owner. Test common delegation, already split identities, and a constraint established before a later conflicting load. Include nested calls, null argument/result, reference arrays, access failure before constraint creation, category failure after successful resolution, retained effects across an abrupt call, and repeated use of a site. Compare JDK stages using fresh loaders and observe actual returned values or effects. Independent adversarial tests must prove resolution did not accidentally constrain a symbolic subclass or each dynamic receiver at the wrong stage.

The deliverable should include an executed caller using these checks. Full class lifecycle orchestration, a general classpath launcher, historical verification, modules, dynamic constants and invokedynamic each require further work. Exact contracts for those can build on this real resolution and dispatch path.
