# Next: class preparation, static state and initialization

Status: proposed direction on 2026-11-04 after `m2-exception-dispatch-review.md`. This note does not authorize production changes. An exact bounded runtime/engine contract and review gate must precede implementation. Full M2 and later milestones remain open.

The body engine now supports reference calls and supplied-Throwable abrupt completion. The next direction should establish owned static state and explicit lifecycle responsibilities before ordinary object construction or VM exception materialization. Existing default-only StaticStorage is useful storage, but is not evidence that a class has been linked or initialized. Existing selected-body entry points must retain their documented host-supplied-state boundary.

Preparation establishes static defaults without executing Java; initialization has separate ordering, recursive-use and failure obligations. ConstantValue handling and class/interface dependency initialization must occur at their specified stages. See [JVMS preparation](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.2) and [JVMS initialization](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.5).

The exact contract should choose a useful bounded preparation/static-service increment first if complete initialization cannot yet be supported honestly. It must settle:

- Registry-scoped ClassId ownership, immutable admitted dependencies, checked static locations and independent resource limits. Retain one logical location per field, preserve reference identities, and expose actual static roots without unchecked writes or name-only class identity.
- A precise separation between allocated defaults, supported preparation obligations, initialization in progress, successful initialization and failure. No public switch may mark unexecuted code initialized. A limited service must name its unsupported verification/loading obligations rather than claim complete linking.
- Field access, final-write authority, descriptor identity and assignment checks for numeric and reference state. Resolve the actual defining declaration rather than attach storage to a symbolic subclass owner. Preserve existing instance-field and protected-access behavior.
- Numeric ConstantValue semantics and the boundary for String constants. String objects and interning require their own real service; do not substitute null or fabricated initialized objects. Reject unsupported initialization prerequisites before claiming successful state transitions.
- A later opt-in engine bridge for static accesses, active-use calls and actual clinit execution through the shared frame engine. Pin dependency order, recursive use, identity-scoped initialization ownership and eventual thread synchronization obligations. Do not reinterpret current same-class helper execution as automatic initialization.
- Abrupt completion and host interruption as distinct cases. Supplied Throwable propagation exists, but ExceptionInInitializerError and subsequent NoClassDefFoundError materialization do not. The contract must define explicit unsupported outcomes and persistent state without silently retrying partial initialization, erasing earlier writes or asserting a Java erroneous state that has not been modeled correctly.
- Bounded iterative dependency traversal, shared execution fuel and work accounting, immutable metadata borrowing and exact commit boundaries. Failed host admission must not publish partial storage; Java execution effects require their own explicit persistence policy.

Use original JDK fixtures for defaults, constants, hidden static declarations, initialization order, recursive access, once-only execution and abrupt completion only to the extent the selected profile implements them. Add synthetic identity, access, finality, resource, invalidation and host-interruption tests. Preserve old entry-point behavior and the complete existing oracle corpus.

Runtime ownership should cover checked state, static storage, dependency planning and lifecycle transitions. Interpreter ownership should cover only the reviewed opt-in bridge and shared-engine scheduling. Root should provide genuine metadata, independent JDK results and retained-state assertions. Constructors/uninitialized references, general library bootstrap, VM exception construction and Java application startup remain separate contracts; none is authorized by this direction note.
