# Monitor execution in a verified application

**Proposed for exact-contract planning after verified application entry is accepted.** Run an ordinary Java 21 directory application whose main and helpers use synchronized methods and blocks. Count its returned values and retained field writes through the public launcher. M2 explicitly requires synchronization instructions. The verifier already checks their operand types. The interpreter still rejects synchronized Code and lacks monitor execution. [M2 charter](../../ARCHITECTURE.md#m2--bytecode-interpreter)

## Why this increment

* The current heap, private unfinished references, selected method identities and iterative frames supply the identities and invocation boundaries needed for one logical Java thread. This yields useful behavior on the public entry path without adding loader privileges.
* Catching VM-produced exceptions would improve nearly every instruction failure, including monitor failures. It needs a distinct contract for the actual bootstrap exception identity, how an object becomes a valid Throwable with observable state, class initialization, permitted stack-trace/message behavior and production failure. Genuine Throwable startup and its library/native dependencies exceed the current closed execution profile. Existing supplied-Throwable dispatch can already exercise abrupt monitor release independently.
* Nonempty launcher arguments and string constants need a genuine bootstrap String representation, exact character conversion and a tested platform-library boundary. Literals also require interning identity across callers and compiled ConstantValue handling. An empty String array already suffices to run the proposed programs. String support remains a separate application milestone.

## Contract to develop

1. Put monitor ownership in the single-session execution service, with stable, opaque keys for actual heap objects (including arrays) and one class monitor per actual defining ClassId in its checked domain. A private class key represents the monitor associated with the declaring class's Class object. The future mirror service must use that same key when an actual mirror reference is used as a lock. Keep general Class literals, reflection and getClass outside this scope. Preserve loader/heap affinity. Use a logical thread owner independent of a frame, a constructor alias or a recursive class initialization activation. [JVMS method invocation](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.invokestatic)
2. Implement monitorenter and monitorexit with checked count changes, identity validation, reentry, null and nonownership outcomes. The private handle of an unfinished constructor reference may identify a lock without promoting the reference or exposing it as an ordinary runtime value. Synchronization methods use the selected method's flags, actual receiver for instance calls and actual declaring class for static calls. Bind the synchronized main through the existing named-class entry, initialization and deferred actual-method invocation. Distinguish initializer synchronization from the separate class-initialization protocol, including ignored initializer flags. Leave legacy entry modes without monitor services explicitly bounded. [JVMS monitorenter](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.monitorenter) and [monitorexit](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.monitorexit)
3. Acquire an implicit monitor only when the resolved body is ready to enter after applicable initialization. Release it once on any normal return or when a supplied Java throw actually escapes that frame. A caught throw in the same frame keeps the implicit monitor. Preserve real invocation PCs, initialization boundaries and construction alias cleanup. For structured locking, plan to enforce both permitted per-invocation balance rules. Explicit lock balance is per monitor, not a global LIFO stack. Attribute the implicit acquisition/release pair to the caller's invocation under §2.11.10. Specify unmatched exit, unbalanced return or escaping throw, replacement IllegalMonitorStateException, and virtual root caller accounting. Tests must distinguish explicit bytecodes in compiler-generated finally blocks from implicit method release. [JVMS synchronization](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.11.10) and [athrow](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.athrow)
4. Bound active identities, ownership depth/count and per-invocation records with checked arithmetic, fallible reservation and exact resource precedence. Charge even repeated operations on the same identity. Require allocation-free cleanup on host interruption, foreign references, panics and exhausted work. Keep already committed Java fields and initialization records inspectable. For null and illegal monitor state preserve the explicit unmaterialized VM-error category in profiles lacking exception production. No fake catch or Throwable. Admission must keep unsupported native/special bodies closed. Thread creation, blocking, wait/notify, memory-ordering claims and the public Thread.holdsLock native remain open.

## Evidence before approval

* Coordinator: launch original javac programs on HotSpot, OpenJ9 and the public CrabSpot entry. Cover aliases, distinct instances, primitive/reference arrays, recursion through synchronized virtual/ordinary calls, an inherited static synchronized helper, named synchronized main and compiler cleanup on early return/break. Use a separate reference-only observer for Thread.holdsLock and class-literal controls. Retain direct stage, effects, class bytes and VM provenance. A successful single-thread trace cannot establish ownership by itself.
* Independently emit verified Code distinguishing null entry/exit, wrong-object exit, balanced non-LIFO release, cross-frame exits, unmatched enter at return, synchronized normal/abrupt release and unfinished-reference monitors. Record both VMs' raw behavior and accepted §2.11.10 choices separately. Use a low-level supplied Throwable to verify identity on caught/rethrown paths; assert monitor counts independently so a no-op implementation fails. For static locks distinguish actual declarer from symbolic subclass and same-spelling owners in different loaders.
* Proposed worker split: one Sol owner implements and adversarially tests the bounded state/identity service. Another integrates it at shared engine preparation, dispatch, frame entry, return and unwind, the main-token gate, and launcher options. Coordinator owns dual-VM fixtures, command-line/effect assertions, and fresh combined gate. Freeze the exact API, the structured-locking rule/order and interrupted-evaluation cleanup before production dispatch. Acceptance covers a single logical thread and supported bytecodes only.
