# Establish real Throwable state and catchable VM exceptions

**Revised priority after equality acceptance.** Build the reusable exception object and propagation path before adding another String method whose invalid-input path still stops at a host failure. Preserve the char-at proposal and its dual-VM evidence as the next library workload. This proposal authorizes reference and contract work only.

A coherent next execution target is one public Java application that constructs and throws a real Throwable subclass, catches and rethrows the same object, then catches fresh VM-produced ArithmeticExceptions from integer and long division/remainder. It must inspect class identity, detail message and cause through Java methods, preserve earlier writes, and expose a bounded snapshot of the actual guest stack at the original failure. Integrate this with existing handler selection, constructor completion, initialization, monitors and heap ownership. Fix the common producer interface so subsequent null, cast, array and monitor errors can use the same path with explicit per-producer semantics.

The minimum runtime addition is a real immutable backtrace payload associated with a canonical Throwable instance, populated by the exact library native fillInStackTrace. It must preserve identity, frame owners/methods/bytecode positions and budgeted storage. Pin the distinction between a user constructor capturing its call stack and a VM error capturing its original failing instruction before internal construction. The existing engine knows those frames. Use real constructor and native boundaries with retained effects and failure handling. Decide ordinary getStackTrace materialization and reference-array clone in the contract after inspecting the supplied StackTraceElement implementation; if those dependencies are separate, expose a read-only host snapshot and make the unsupported Java query explicit. Empty fabricated traces must never pass as successful capture. [Throwable API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Throwable.html)

The inspected Zulu Throwable initializer executes the Class assertion query already supported by the equality increment, creates real StackTraceElement[] and Throwable[] sentinels and invokes Collections.emptyList. Collections initializes real EmptySet, EmptyList and EmptyMap instances. Throwable's constructor runs Object, sets cause to itself, sets stackTrace and suppressedExceptions from those statics, then dynamically invokes fillInStackTrace. The Java synchronized wrapper invokes its private native and resets the public lazy stack field. ArithmeticException delegates through RuntimeException and Exception. These operations provide concrete evidence for real object state, allocation, actual constructor chains and synchronized entry. No inert projection, precompleted initializer or substitute Java return supplies them.

For the first VM producer, retain the original idiv/irem/ldiv/lrem offset and operands' established effects, construct the canonical runtime exception through an authenticated engine continuation, and resume exception dispatch at that original instruction. Decide interruption, constructor failure, recursive VM failures, resource ceilings and allocation failure before implementation. Preserve monitor ownership while internal construction runs, then apply normal local catch or frame unwind semantics to the produced object. Include independent user-created and VM-created exceptions, catch mismatch, same-object rethrow, two fresh failures, handler failure, constructor/initializer escape and all prior supplied-exception regressions. Message policy needs its own documented contract; Java specifies ArithmeticException on integer division by zero but does not fix a message string. [JVMS idiv](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.idiv)

Reference work should capture actual Java 21 class bytes and native declarations for Throwable, Exception, RuntimeException, ArithmeticException, StackTraceElement, Collections and the three empty containers, including superclass/default-interface closure. Run both VMs with original programs that observe class, message, cause, rethrow identity, trace top and retained writes. Record permitted diagnostic variation separately. Use explicit symbolic exceptions for constructor/resource failures, never allow a host error to become a successful Java catch. A first contract may begin with ArithmeticException, but the implementation structure must accept the other existing VM exception kinds without replacing the dispatch loop or introducing another registry.

This priority follows the full JVM target. General catchable VM failures are required across arithmetic, object, array and monitor operations. In contrast, the inspected String.charAt failure is a Java library chain through Preconditions, Number[], Integer.valueOf and formatting. Starting at that chain would pull formatting and boxing bootstrap into the next contract while leaving the common VM error path open. The in-range charAt groundwork remains useful: its wide path needs an exact isBigEndian native, and even valid indices initialize three Function instances and three BiFunction adapters. Return to the complete text workload after the shared Throwable path is explicit.
