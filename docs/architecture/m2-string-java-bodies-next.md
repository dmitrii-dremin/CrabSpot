# Execute the platform's String length and emptiness methods

**Proposal after String-constant acceptance.** Run the supplied Java Code of `String.length()I`, its `coder()B` helper and `String.isEmpty()Z` on literal and argument values through the verified directory launcher. This is the smallest useful step from exact UTF-16 pool values to a real platform String layout and real String initialization. Planning requires acceptance of the String-constant gate; this proposal does not dispatch production.

## Evidence from the supplied platform

Both VMs supplied their actual `jrt:/java.base/java/lang/String.class` bytes. Disassembling each captured file by path identifies two different initialization contracts.

Both length bodies read the backing byte array, call coder and shift. On both default configurations the measured UTF-16 lengths for empty, A/NUL/U+00FF, A/euro/rocket, one lone low surrogate and rocket were 0, 3, 4, 1 and 2. The corresponding coder/byte counts were 0/0, 0/3, 1/8, 1/2 and 1/4. Latin bytes were `4100ff`, mixed bytes `4100ac203dd880de` and the lone unit `ffdf`. With Zulu compact strings disabled every example used coder 1, including the six-byte Latin example `41000000ff00`. Each configuration had a genuine zero-length ObjectStreamField array and a nestmate comparator that compared a/A equal.

All three reference runs of the compiled `compact.Entry` yielded `63/0/3/4/1/2/0` without arguments and `127/0/3/4/1/2/3` with two arguments. On the integrated CrabSpot String-kernel executable the same application stopped at its first length call, `MainEvaluation` at `main@33`, with opaque String state. For acceptance, bind the compatible initializer and private layout together before granting field or body access. Feed the actual OpenJ9 shape to the new binder as an incompatible-image control. Record OpenJ9's application results as an independent behavioral reference. Qualify hosted Temurin builds by inspecting and running their actual supplied images before claiming coverage. Compact-disabled Zulu remains a reference configuration until the implementation supports and tests its storage policy.

## Immediate implementation boundary

1. **Select and verify the library layout.** Resolve exact bootstrap field/method IDs, signatures, flags and the supplied Code roles on the same registry/heap. The layout adapter initially supports the evidenced compact byte-array representation. Before freezing implementation, identify supported vendor builds by independently checked semantic shapes or explicit identified binary revisions. Reject an incompatible layout when the new capability is requested; keep the previous kernel available for valid role-only test images. No name-only binding, replacement of Java methods, assumption that every Java 21 platform has Zulu's fields, or unverified execution of platform neighbors.
2. **Give each String genuine, stable backing storage.** Preserve exact UTF-16 contents, cross-loader canonicality, first-receiver identity and existing CP-site semantics. Associate an actual managed byte array and coder with a given String in this profile. With compact encoding, all units ≤255 may use one byte per unit. Other values require a consistent supported endian layout and two bytes per unit, including isolated halves. Use a single agreed compact policy for an image, coherent with the Code that initializes COMPACT_STRINGS. Check overflow and actual byte/array/instance limits before publishing. If storage is materialized lazily, the first field access must have a documented failure order, and a failed materialization must leave the already-issued String, pool and site usable under the preceding contract. Keep every byte array reachable through the String's heap-child/root traversal. Cross-heap handles, mutation through any exposed alias, raw field setters and construction of fabricated ordinary Strings must not invalidate an intern key. Test a reservation failure with earlier values already pooled, an attempted backing mutation and a subsequent equal literal.
3. **Run genuine Code and initialization.** Allow the exact selected length, isEmpty and coder bodies and the necessary checked accesses to actual value/coder slots. Keep ordinary decode, reservations, instruction fuel, per-frame identity, loader resolution and error provenance. The real String initializer sets COMPACT_STRINGS, allocates an empty ObjectStreamField[], constructs String$CaseInsensitiveComparator and stores the public comparator. Prove, witness and admit those bootstrap implementation dependencies and their hierarchy, without adding their names as general application imports. An array of ObjectStreamField does not actively initialize its component. The comparator has a private constructor that invokes Object.<init>. Its NestHost names String and String's NestMembers includes the comparator. Resolve that access with loaded same-runtime-package, reciprocal nest membership tied to canonical ClassIds; a dollar sign, package match or the mere presence of a metadata attribute confers no access. Either implement this normal checked nest relation with a bounded lookup or make it a separately tested prerequisite. Preserve default-method-superinterface initialization order, final-static write authority and a precise failure on unresolved or inconsistent metadata. [JVMS access control](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.4), [JVMS initialization](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.5)
4. **Prove the path, including failure.** Use the physical CLI and public API on a genuine Java 21 directory application. Observe lengths and emptiness of empty, Latin-1, mixed, paired, lone-surrogate, duplicated and noninterned argument Strings, plus identity before and after pooling. Independently inspect the actual byte-array lengths and contents, both coders, instance graph edges, initializer statuses and initialized comparator/static array. Pin the exact body/PC and prior effects at a one-short Code, frame and instruction budget. Negative controls include a misdeclared backend field, insufficient array bytes, missing local helper, false/missing nest membership, denied external private access and unchanged closed-profile behavior. Precisely classify a caller-supplied modified body as rejected by its declared compatibility profile or execute its actual instructions with checked access; it must never receive a canned length by name. Archive original and regenerated application inputs and both JVM observations independently. Report the genuine per-platform proof/initialization inventories and remaining first unsupported site in words.Entry.

## Sequence toward all four methods

After this gate, add genuine Class.desiredAssertionStatus execution for evidenced bootstrap roles. The Zulu body reads the mirror's classLoader field and takes the bootstrap-null branch to a static native; that active use also requires truthful Class initialization/native registration. Never pretend an application-loader mirror has the null bootstrap loader. Bound assertion settings, module/loader distinction, structured native registration and UTF16 endianness before enabling helper initializers. The existing two-VM assertion results differ on arrays under -esa. Use explicit semantic controls for each supported setting. Then prove genuine distinct-object equals and in-bounds charAt, including the actual formatter/Preconditions dependency chain; separately specify wrong-index handling. For multi-unit hashCode, scope the supported Unsafe/array-layout, byte-order and shared-secret bootstrap obligations from measured library Code and genuine machine facts. No uniform fake array scales, no global initialized bits and no VM shortcut for vectorizedHashCode standing in for the promised Java path. Final evidence for these later increments must include the real mixed-unit words.Entry result `63/-1902190381/-1902190381/true`, content equality on separate instances, a zero Java hash cached correctly and same receiver re-use.

The runtime owner could implement a bounded String storage adapter, scalar field access and nest validation. The execution owner could integrate selected Java body entry, verified internal dependency provisioning and independent tests in the existing call/initializer machinery. The coordinator owns dual-VM controls, actual image provenance and the combined gate. General constructors/encodings, arbitrary String methods, arbitrary platform access, JNI, reflection and catchable VM-created exceptions remain open.
