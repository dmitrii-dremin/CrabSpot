# Next: whole-method Code validation and verifier foundation

Status: proposed direction after the bounded construction approval on 2026-11-04. This note does not authorize production changes. The technical director must freeze an exact scope, API, policy and acceptance contract before workers implement it.

The engine now executes substantial class, interface, initialization and construction behavior. Its dynamic checks intentionally cover only executed paths. The next coherent step is a reusable whole-method validation foundation, followed by verification of type states. This advances the full JVM target without mistaking a successful constructor execution or opcode count for verification.

The governing distinction is between instruction/operand static constraints and control-flow/type constraints. Stack-map information supplies verification states; decoding it is not proof that those states are sound. The next contract should map its exact checks to [JVMS 4.9.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.9.1), [4.9.2](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.9.2), [StackMapTable](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.7.4) and [verification by type checking](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.10.1), with a named unresolved boundary for every deferred obligation.

The first bounded implementation should examine an entire method's Code independently of whether an instruction is reachable or currently executable by the interpreter. Reuse the existing decoder and class-file inspection model. Add file-local operand checks against constant-pool kinds, descriptors and class-file version; local-index/width limits; invocation-count and array-dimension relationships; and Code-associated instruction-boundary checks, including handlers and stack-map offsets/uninitialized-new locations. The exact contract must distinguish parser guarantees it may rely on from checks needed for publicly mutable inspection metadata. It must not resolve or initialize classes, allocate Java objects, invoke Java code or manufacture VerifyError objects.

Use an explicitly named partial-validation result rather than a VerifiedClass or VerifiedMethod token. A useful first module or crate may depend on classfile and bytecode; runtime identity/type relations should enter only when the later type checker actually needs them. Retain immutable metadata or compact indices rather than duplicated descriptors, handler tables or expanded frame histories. Bound actual instructions, metadata entries, descriptor work and retained output with checked arithmetic and fallible reservations. Long shared descriptors and compressed stack maps must not create unaccounted amplification.

Integration must be deliberate. Existing inspection and method-body APIs are not silently reclassified as verification gates, and diagnostic-order tests must not be weakened. The contract should decide whether the initial service is independently callable or introduced through a new explicit preparation profile. Only a subsequent reviewed type-state checker can establish stack/local types, merges, exception-edge states, constructor initialization proofs and required cross-class relations. Historical inference and version-specific rules need an explicit inventory; a Java 21-first checker must not imply support for every historical form accepted by the parser.

The coordinator should supply positive checks over all genuine fixtures, including instructions beyond the current execution profile, and original malformed bytecode that a JDK rejects even when the defective instruction is unreachable. Differential harnesses must distinguish class-format, verification, resolution and execution failures and force the intended JDK validation stage; diagnostics text is not the oracle. Workers should independently test typed constant-pool mismatches, wide/local boundaries, version/tag distinctions, handler and frame offsets, uninitialized-new references, malformed unused blocks, resource exhaustion and repeated deterministic validation. Preserve existing execution comparisons as regression evidence.

This is a prerequisite proposal, not the end of M2. VM-produced exceptions, String interning/constants, native/core-library services, synchronization, full loading constraints, GC and application startup remain required. Once the static foundation is accepted, proceed to an exact type-state verification contract rather than indefinitely expanding partial validation under a full-verifier label.
