# Next interface and default-method increment

Status: design direction only, following the bounded approval in `m2-virtual-calls-review.md`. This does not authorize another implementation. A concrete API/semantic contract and explicit technical authorization are required before dispatch; architectural work needs no further user permission.

The next coherent execution step should complete the currently explicit interface-method fallback and add invokeinterface for numeric/void bodies. This reuses registered MethodIds, per-frame constant pools, receiver handles and the shared bounded call engine. It directly expands usable Java dispatch while keeping constructor, initialization and verification responsibilities visible.

Define one reusable interface-candidate analysis for class Methodref fallback, InterfaceMethodref resolution and receiver selection. Preserve the distinction between resolution and dispatch: class declarations take precedence; interface candidates require a maximally-specific analysis, not the first matching declaration. Deduplicate diamond paths by identity and account for abstract redeclarations that suppress less-specific defaults. Resolution's permitted choice between abstract candidates must not accidentally determine dispatch or observable results. An interface's public non-static Object-method resolution case needs explicit registered Object metadata, never a fabricated implementation. The normative starting points are [method resolution](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3.3), [interface resolution](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3.4) and [method selection](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.6).

Pin class/interface membership and subtype queries to the existing admitted identity graph. Keep runtime-package/loader rules, named-module and nest limitations explicit. Access, staticness, null, receiver-interface compatibility, selected-method visibility, abstract/default-conflict and unsupported-native ordering require their own testable contract. invokeinterface can legally name a private interface method; a blanket private-is-static-style rejection would be incorrect. Its operand count and reserved zero byte also need descriptor-aware validation, including category-two arguments. Use [JVMS invokeinterface](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.invokeinterface) to settle those rules before code.

Selected concrete interface bodies must be prepared through a deliberate resolved-call mode. Do not merely remove the existing interface-root guard and pretend every externally selected interface method is executable. Preserve numeric explicit parameters/results, implicit receiver transfer, correct declaring-interface constant pools and field origins, all cache-mode guards and caller provenance. Reuse the context's symbol/work policies; candidate dominance and graph searches must be iterative and charge work before expansion. A bounded quadratic dominance algorithm may be acceptable initially if its costs and failure limits are explicit; no hidden unbounded transitive closure or recursive traversal is acceptable.

Acceptance should include genuine Java default inheritance, class implementations overriding defaults, inherited class methods, diamond reuse, interface-to-interface calls and private interface helpers within the supported opcode profile. Synthetic cases must cover conflicting unrelated defaults, abstract redeclarations, missing implementations, nonpublic selected methods, wrong receiver interfaces, same-name/different-loader types, Object-method fallback and exact budgets. Differential oracles must separate valid Java results from malformed bytecode and host-policy errors. Preserve all accepted earlier comparisons and failure regressions; record new hosted checks separately.

Ordinary super/private invokespecial can follow under another bounded contract. Constructor invokespecial needs uninitialized-reference/constructor protocols, and application startup needs real lifecycle/initialization work. Reference assignability and broader values, exception objects/dispatch, monitors and verification remain required progress toward full M2/JVM conformance. Completing interface dispatch alone will not close those obligations.
