# Next: reference arrays and their bytecodes

Status: proposed direction on 2026-11-04 after the bounded approval in `m2-reference-fields-review.md`. This note does not authorize implementation; an exact runtime API, storage accounting and instruction/error contract must precede dispatch. Full M2 remains open.

After checked instance fields, add reference-array storage and anewarray, aaload and aastore to the existing runtime-aware engine. This makes the structural array identities and component relation executable for real reference-array values. Numeric wrappers can allocate arrays, store this or primitive arrays, retrieve aliases, use fields/calls/casts and return numeric results. Reference method signatures and constructors are not prerequisites.

Each allocation must retain the actual checked array type, including rank, nominal/primitive leaf and defining loader. The component of a reference array may itself be an array type: an outer int[][] contains references to int[] values, while a primitive int[] remains a different payload kind. No fabricated ClassId or class mirror is needed. One-dimensional allocation must initialize every component to null and publish its handle only after complete reservation and checked accounting.

Share the existing array count, per-array length, total element and payload-byte quotas across primitive and reference arrays. Pin the reference-slot byte accounting explicitly in the exact contract; do not label it a complete measurement of process memory. Preserve primitive-array APIs and error behavior. Make arraylength work for both actual array payloads, while primitive-specific operations still reject reference arrays. Constructors, element initialization and recursive multianewarray allocation remain separate work.

Use the accepted type relation for checked stores. Keep raw public APIs from bypassing component checks; the heap commit boundary must validate array ownership, kind, index and source handle before one-slot mutation. Allocation and store failures must preserve earlier state. A successful non-null store adds an immediate child edge; aliases, self-links and cycles remain distinct per-location results in the existing borrowed children iterator. Enumeration is not tracing or collection.

The exact instruction contract must retain target resolution/access before a negative-size outcome for anewarray. aaload has null then bounds outcomes. aastore has null, then bounds, then incompatible component outcomes; ArrayStoreException is a genuine Java outcome here, unlike the host-only incompatible-field diagnostic. See [JVMS anewarray](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.anewarray), [aaload](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.aaload) and [aastore](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.aastore). Host-invalid handles and unsupported malformed rank encodings need explicit policy ordering alongside those Java outcomes.

The public type service must recognize the new actual array payloads so checkcast/instanceof and checked instance fields work with them automatically. Runtime-aware array operations should reuse the shared context, universe, origin bindings and budgets; no second engine or alternate nominal resolver. New reference-array operations remain unavailable through older entry points unless a separate contract explicitly extends them.

Required evidence should cover nominal/interface covariance, exact primitive-array components inside reference arrays, unequal ranks, rank limits, inaccessible/missing component types, loader-separated equal names, null/default elements, aliases/cycles, array-as-field values and nested array retrieval. Test shared quota boundaries and overflow, late store failures retaining old elements/children, null/bounds/type precedence, current-frame component resolution, deep iterative relations and deterministic drop. Add genuine JDK comparisons for numeric wrappers and preserve all earlier fixtures and outcomes.

Reference arguments/results and ordinary object construction can then build on actual typed reference storage. They still require separate loading-constraint, invocation, uninitialized-reference and lifecycle contracts. Full M2 is not completed by adding these three bytecodes.
