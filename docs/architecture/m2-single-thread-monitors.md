# Single-thread Java monitor execution

**Frozen for bounded implementation dispatch, 5 November 2026.** The coordinator and both component owners completed readback of the exact APIs, ownership, accounting, execution order and reference differences. Run real synchronized Java Code in the existing engine under one logical Java thread. Preserve Java effects and report the actual failing instruction when an ownership check fails. Acceptance requires frozen component reviews and a fresh combined gate.

## Entry and compatibility

Add the following public surface. Integral ceilings are inclusive u64 values. Derive Copy, Clone, Debug, Eq and PartialEq on limits/resources. Use the named defaults in field order.

```rust
// crabspot-interpreter
pub struct MonitorLimits {
    pub max_steps: u64,            // 1_048_576
    pub max_active_monitors: u64,  // 16_384

pub enum MonitorResource { Steps, ActiveMonitors, ActiveClaims, Recursion }
pub enum MonitorError {
    Limit { resource: MonitorResource, limit: u64, required: u64 },
    AccountingOverflow { resource: MonitorResource },
    AllocationFailure,
    InvalidState(&'static str),

// additive crabspot_runtime::VmExceptionKind::IllegalMonitorStateException
```

## Identity and frame accounting

Use `Object(HeapRef)` for a non-null ordinary object, an array or the actual heap identity behind a private unfinished constructor reference. Validate it in the current heap before using it. Do not expose an unfinished alias as an ordinary Reference or convert/promote its other frame aliases. Use `Class(ClassId)` for the monitor associated with the Class object for the **actual selected static method's declarer**. ClassId includes defining identity. Distinct definitions with equal names have distinct locks. No new Java object, class initialization or CP resolution occurs to create a lock key. The profile cannot currently obtain a Class mirror in application bytecode. A later mirror implementation must map a Class object reference and its declaring-class key to the same monitor before enabling those operations together. Keep class initialization's own coordination separate. [JVMS synchronization and method invocation](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.11.10)

The service maintains the total positive acquisition count per live identity. Each Java frame owns its explicit positive acquisition count per key. A synchronized callee also holds one private implicit receipt for its invocation. The caller's invocation logically performs the paired implicit entry and exit. No user instruction in the callee may consume that receipt as an explicit acquisition of its own. The host root has the corresponding virtual caller. A frame debits only its own explicit count. A missing count is a Java ownership/balance error even if the underlying thread currently owns the key through another invocation. This chooses **both** optional structured-locking rules. Balance is per key, so enter A, enter B, exit A, exit B is legal. Never impose a LIFO rule across different objects. [JVMS structured locking](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.11.10)

A live claim is one positive explicit (frame, key) row, or one outstanding implicit receipt for a synchronized callee. Reentry on one explicit row increases per-key total and local counts, without creating another claim. Distinct synchronized invocations create separate receipts even when they use one key. Retire zero rows/keys immediately. Frame depth may serve as a private frame identifier only while an invocation owns that depth. Every successful return or supplied-throw frame pop must have consumed its receipt and cleared all its explicit rows. The service can maintain per-frame outstanding explicit row/count scalars for O(1) completion checks; avoid rescanning frame locals, operand stacks, ancestor frames or the whole monitor table per instruction. Use scalar-key maps, checked actual-demand growth and iterative teardown. Monitor identity never includes a PC, a method name, an allocation site or a constructor alias tag.

The internal cross-crate split keeps monitor storage private to the interpreter. Add `monitor.rs` with `pub(crate) MonitorKey::{Object(HeapRef),Class(ClassId)}`, `MonitorLedger::new(MonitorLimits) -> Self`, and `MonitorFailure::{Java(VmExceptionKind),Host(MonitorError)}`. Each operation takes `&mut self`, a zero-based frame depth `usize`, and (except finish) a key. The names are `enter_explicit`, `exit_explicit`, `enter_implicit`, and `finish`; all return `Result<(), MonitorFailure>`. Java errors arising at the ledger boundary map only from the direct Java variant. Validate heap keys with the existing `validate_root`. Validate the canonical selected static owner against the session's admitted class snapshot using the existing initialization class check before an implicit static acquire. No symbolic selection or UTF work is repeated. No public runtime monitor handle is needed.

Keep `Option<MonitorLedger>` in evaluation-local engine state. The ledger alone has a scalar-depth index to per-invocation records. Zero-depth means the first Java frame. Use the current frame index for c2/c3 and finish, and the prospective index before publishing the callee for enter_implicit. There is no change to legacy Frame layout. Create a depth row only on its first actual claim and retire it after its last claim. Its size is bounded by ActiveClaims. A fresh implicit activation cannot already have a depth row (private InvalidState, including a duplicate receipt). Successful frame exits always call finish before reusing a depth, including constructor and initializer boundaries. A host interruption ends the evaluation and drops the entire ledger. Reserve staging for the outer depth row, per-frame explicit row and global identity before any logical mutation; private reserve failure at any stage leaves all previous ownership unchanged. No public read/write ownership query. Tests of actual count/identity state can live inside the private module; public negative effects and exact resource controls must independently exercise the same service.

Add a constant-time, uncharged `MonitorLedger::check_new_frame(&self, depth: usize) -> Result<(), MonitorFailure>`. After successful ordinary activation preflight and reservation, verify the depth is vacant on **every** monitored frame publication, including ordinary, constructor, clinit, resumed call and named root. Check before implicit entry. Implicit entry itself also rejects private stale/duplicate state. This guards against a stale depth later masquerading as a legitimate explicit reentry. No per-frame heap allocation or work charge for this scalar guard on a frame which never acquires a monitor.

## Transfer order

1. In monitor mode c2 and c3 consume the next instruction's fuel at the ordinary point. Pop exactly one generic reference using the existing private frame kind/type check. Missing/wrong computational type, invalid private null alias and foreign/stale heap errors follow the original trusted-reference conventions at the actual PC. A genuine null causes the existing direct `UnsupportedVmException(NullPointerException)` at this PC before any monitor charge. For a validated non-null c2/c3 pay one monitor step, then enter/exit. A positive explicit exit requires both thread ownership and that frame's own positive count. A genuine missing owner or missing frame acquisition gives `UnsupportedVmException(IllegalMonitorStateException)`. A disagreement between private ledger totals, receipts or validated frame state is a host `InvalidState`. A failed c2/c3 must never publish partial ownership. [monitorenter](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.monitorenter) and [monitorexit](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.monitorexit)
2. For a normal method inspect the **selected** body's synchronized flag in preparation, including warmed method caches. Preserve existing static/instance eligibility, native-before-sync rejection, argument/layout/prepared-Code/frame/slot checks, receiver selection, loading constraints and construction roles. Initializer roles continue ignoring incidental synchronized flags on clinit; constructors still obey parser restrictions. An invokestatic or named application main must complete its existing target/named initialization before acquiring the deferred synchronized-method monitor. All fallible frame/cache/activation provisioning which can be done before implicit acquisition must be done first. Acquire once at actual activation, immediately before publication of that frame, using the actual receiver or selected declaring class. No monitor step for resolution, preparing selected Code or suspending an invocation. A call that fails before activation never acquires. A failing implicit acquisition on a nested call reports the caller's actual invoke PC/site, including a deferred b8. For an application/static root with no caller, preserve the actual selected method identity with no fabricated PC. A named class already Completed followed by root acquisition failure is MainEvaluation.
3. For all six typed return instructions, first perform existing operand/return/construction protocol validation, including checking a constructor's chain/return when applicable. Then perform the completion check below before frame pop, caller alias promotion, initializer completion, result transfer or return to host. A successfully transferred return keeps the existing narrowed primitive/raw floating bits, category widths or reference identity. A balance error at return replaces the intended return with the direct unmaterialized IMSE diagnostic at that actual return PC.
4. On an explicit supplied Java throw, perform existing validation and charged exception table search on the current frame. A matching same-frame handler keeps all implicit and explicit ownership. Recheck the frame only when the search determines it will escape, after existing dispatch/unwind funding but before popping ordinary/constructor/initializer frame, invalidating caller aliases or marking the initializer erroneous. Normal close releases its implicit receipt exactly once before caller search; keep the original throwable and caller invocation PC. A balance failure replaces the supplied throw with the explicit unmaterialized IMSE policy at the escaping frame's search PC. The engine does not pass the replaced throwable to a caller handler or record it as an initialization cause. Existing interruption cleanup can mark an in-progress initialization Aborted. Preserve the true method/call-site/initialization diagnostics. Host failure while searching handlers is still a host interruption. [JVMS athrow](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.athrow)
5. Completion of a frame with zero outstanding explicit claims and no implicit receipt consumes zero monitor steps. Otherwise pay **one** step for that frame boundary. First reject any positive explicit balance as IMSE. If balanced, validate and release its one implicit receipt, updating the per-key count/active-claim count atomically. An implicit synchronized invocation thus normally costs two steps total (entry and exit). A balanced explicit pair costs two; its ordinary frame's later balanced completion is free. Same-frame handler installation never consumes a monitor completion step. Every host error, Java production refusal, limit, panic or session drop discards the complete evaluation-local ledger without allocation or further fallible policy charges. It cannot erase committed Java heap/static effects. A later valid evaluation under the same session must prove no leaked ownership. This is an explicit single-thread profile with supplied exception dispatch; VM-created IMSE/NPE identities, waits, contention and Java memory-order observations remain open.

## Resource rules

All new resource counters start at zero for each evaluation. An operation subject to a step charge first computes and funds used_steps + 1, independently of whether the operation later fails. A rejected step retains the previous counter and ownership. Null/reference validation precedes it; a zero-step policy can still report NPE for genuine null. Non-null semantic checks and storage publication follow. For acquisition check, in order, the prospective active key count, active claim count, recursion count for that key, then scalar map/receipt coherence and fallible actual-demand reserves before publishing any change. The recursion cap bounds the total thread depth for that key across all methods. Required amounts report would-be values, never capacity. Overflow at a step/counter check reports its resource. Arithmetically impossible private count inconsistencies on release or frame reuse are host InvalidState. Per-frame acquisition count cannot exceed its key's total. A quota failure keeps all prior steps, existing counts and Java effects; private allocation failure publishes neither a key nor a claim. No reservation by configured maximum. Each operation is a constant number of fixed-width key lookups plus actual amortized growth, completion is O(1), and forced teardown is O(actual bounded allocated state). Do not use host mutexes, park an OS thread or leave ownership in a static global map. No per-evaluation policy is reset at a nested invocation or initializer boundary. Legacy execution allocates no monitor table entries.

## Evidence and interpretations

The development fixture archive records 40 observations per VM from Zulu HotSpot 21.0.7 and OpenJ9 21.0.13.0. Both report the original synchronized application counters 1/2/1/9 and six released locks. Both report distinct actual declaring-class locks across two defining loaders (`0000/1000/1010/1010/1010/1000/0000`). They accept balanced crossed locks and an unfinished allocation as a lock. Their six balanced typed returns and same-frame catch/rethrow preserve the return value or supplied identity. An ordinary and a flagged clinit see no implicit acquisition, a genuine synchronized static helper sees one. On null monitorenter the real JDK raises NPE; CrabSpot's public launcher must record its genuine unsupported materialization at offset 11 and the retained earlier write.

Raw malformed-locking outcomes require separate columns. With an unbalanced return, HotSpot produces IMSE and releases, while OpenJ9 returns the corresponding typed value and retains the lock. With an unbalanced abrupt escape HotSpot substitutes IMSE while OpenJ9 preserves the original reference. Both VMs allow an explicit release of the implicit synchronized lock through their post-exit marker and fail at later method completion. CrabSpot's selected rule rejects that c3 immediately through the per-invocation explicit-balance check. Record the authorized interpretation and phase/effect difference. It must not be counted as a matching reference outcome. Preserve the initial unsupported synchronized-main/unsupported c2 controls as historical observations. Do not add Thread.holdsLock or general Class constants to make the reference observer run inside CrabSpot.

The additional eleven direct-main raw programs use only supported imports and a separately loaded observer. Require their physical CLI and typed public-effect replay. Keep each reference VM's direct-launch status, observer fields/ownership, raw byte digest and bytecode failure site. A synchronized instance method permits the callee to identify its own receiver without a class mirror, so the implicit-only c3 divergence can also be observed directly through the product. Keep reference observations requiring a Class mirror, native or extra loader separately labeled.
