# Next: bounded multidimensional allocation

Status: historical direction, superseded by the exact contract in `m2-multidimensional-arrays.md` and bounded approval in `m2-multidimensional-arrays-review.md` on 2026-11-04. The rationale below is retained; the next proposed increment is `m2-reference-calls-next.md`. Full M2 remains open.

Implement multianewarray next, using the accepted structural types, primitive/reference payloads, explicit universe and current-origin resolver. This completes multidimensional array allocation without first widening method signatures or introducing loading-constraint and return-type obligations. Reference parameters/results should follow as a separate invocation contract; object construction still needs uninitialized-reference and lifecycle protocols.

The exact contract must distinguish the actual array rank from the requested number of allocated dimensions. Allocate only that prefix, preserve the full actual type at every node, use primitive payloads only when allocation reaches a rank-one primitive leaf, and leave the last reference components null otherwise. Resolve/access-check the array component identity before Java negative-size handling. Check every supplied dimension for negativity, even after an earlier zero; a zero suppresses deeper allocation, not validation of remaining counts. See [JVMS multianewarray](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.multianewarray).

Preflight the complete reachable allocation geometry with checked arithmetic: number of arrays, per-array lengths, aggregate elements and typed payload bytes across both payload kinds. Empty dimensions and zero-length child arrays need explicit accounting. Existing array quotas should bound the whole operation; a new unbounded work queue or speculative exponential allocation is unacceptable. Pin whether geometric/preparation work also consumes the cumulative context work budget, with inclusive boundary tests. Keep rank and temporary dimension state bounded by 255 and traversal/build/drop iterative.

Prefer transactional publication for the host resource policy: validate types/dimensions, preflight quotas and reserve/stage all new payloads before making any new handle reachable or changing public counters. Failed allocation should leave existing objects, arrays and edges unchanged. Staged internal links may use only checked future arena indices and the current heap identity/generation; no external callback may observe them before final commit. This is a proposed host-failure policy, not an implementation of Java OutOfMemoryError, tracing or reclamation. The exact design must demonstrate bounded temporary memory and private failure tests before approval.

The existing runtime-aware loop should extract dimensions in JVM order, call one checked service with the current declaring origin, and push the resulting outer reference. Keep prior entry points gated, retain ordinary fuel/stack/frame limits and preserve a completed allocation if a later instruction fails. Use the existing explicit array Java versus host diagnostics; do not infer categories from nested errors.

Evidence should include one requested dimension, partial versus complete rank, primitive and nominal/interface leaves, rank 255, zero at each position, negative counts after zero, malformed dimension operands/CP targets, access/loader identity, all shared quota boundaries and arithmetic overflow. Genuine JDK wrappers should prove c5 emission and compare numerical shape/default/alias behavior and failures. Inspect every reachable allocated type, length, element/child order and shared total, with deep nonrecursive drop and no constructor claim.
