# Next: allocation and constructor reference protocol

Status: historical proposal fulfilled by the bounded contract `m2-construction.md` and approval `m2-construction-review.md` on 2026-11-04. The obligations below record the design questions that led to the accepted increment; they are not a new implementation authorization. Full verification remains open, with the next proposed foundation in `m2-code-validation-next.md`.

Checked ordinary-instance storage, reference transfer, special-call resolution, supplied exceptions and active-use initialization now provide most supporting services for real Java object construction. The next coherent execution increment should address new and constructor invokespecial together, rather than exposing default-filled storage as a constructed Java object. Keep independent execution in the existing engine and preserve explicit host-supplied object APIs.

The exact design must resolve these obligations before dispatch:

- Allocation first requests initialization of the class actually named by new, through the existing scheduler. Checked class identity/access, concrete-class eligibility, quota failure and allocation order require explicit diagnostics. Preserve the original instruction and one fuel debit across suspension.
- Distinguish ordinary references from uninitialized allocation references and constructor-local uninitializedThis. Identity includes the actual allocation, not merely its class or a repeated bytecode offset. Existing public Value/heap services must not accidentally accept an uninitialized reference as an ordinary object.
- Constructor resolution must name the correct declaring constructor and restrict this/super chaining appropriately; constructor roles and cache hits need separate eligibility from ordinary special calls and class initializers. No hardcoded skipped Object constructor may certify success. Explicit supplied core metadata and an actually executed lawful base constructor are required.
- Pin the dynamic enforcement versus verifier boundary. Merely tagging allocation values does not implement stack-map verification, all control-flow merges or Java constructor legality. If a bounded safe execution profile cannot enforce a case, reject it explicitly. Do not claim full verification from successful runtime checks.
- Define allowed uninitialized-value movement, alias conversion on a successful constructor invocation and exceptional invalidation. Per-frame state matters: a superclass constructor can complete while the caller is still constructing the object, and a legitimate ordinary reference may escape after the required chain step before the outer constructor returns. A single global heap initialized bit would not express those distinctions.
- Define field writes and final authority under the actual constructor role, including the precise before-super restriction and own declaring fields. Helpers, unrelated constructors and ordinary bodies must not receive a raw final-write bypass. Check that references cannot enter fields, arrays, static roots, ordinary calls or host outcomes before the supported protocol permits them.
- Preserve exception/handler semantics, prior visible effects, failed-constructor aliases, class initialization state and host interruption cleanup. No rollback or fabricated exception should conceal partial construction. Allocation is persistent under the current noncollecting heap policy; account for roots and orphaned allocations honestly.
- Share existing frame/slot/Code/fuel/lookup policies and add only justified bounded construction bookkeeping. Avoid an unbounded alias registry or recursive execution. Existing body profiles and supplied initialized-reference boundaries need explicit compatibility decisions.

Root should provide original JDK construction cases with superclass/this chaining, hidden fields, final instance values, mixed/reference arguments, aliases, virtual calls after the permitted chain stage, class-initialization traces, and supplied exceptions before/after visible writes. Synthetic cases must exercise illegal early use, repeated construction attempts, wrong constructor owners/roles, same-class distinct allocations, abrupt alias invalidation and exact resource boundaries. Java/JDK-only driver construction must remain separate from tested CrabSpot execution.

If the exact design identifies a necessary verifier or frame-value prerequisite, implement that concrete prerequisite with an explicit acceptance gate first. String interning, VM exception materialization, library bootstrap, monitors and application startup are not implicit parts of this proposal. Full M2 and full JVM conformance remain open.
