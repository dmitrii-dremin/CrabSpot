# Next proposal for modern class type verification

Status on 2026-11-05. Exact contract planning follows acceptance of the modern method checker. Implementation requires director readback of that contract.

The next deliverable should answer whether one canonical loaded class or interface passes the modern type checker in a specified immutable environment. Today a caller must choose and check each declaration. A valid entry method can coexist with a second method that fails verification. The coordinator's current corpus loop illustrates the missing class-level operation. The specification checks every method and the superclass condition, with a distinct base case for the bootstrap Object. Verification can require facts about other classes while their own checking and preparation take place separately. [JVMS 4.10.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.10.1) and [JVMS 5.4.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.1).

The exact contract should settle four decisions.

1. Define the obligations of a modern class type proof. Inventory the parser's already checked class-format constraints, the retained hierarchy facts including final superclass, the selected bootstrap Object rule, and the verified declarations including abstract/native methods and constructors. Pin the ordinary class, interface and module descriptor boundaries. Give class version/preview checks their own entry point so an empty historical class cannot obtain a modern proof by an empty method loop. Describe the assumptions inherited from canonical immutable registry admission, including class-level bootstrap table bounds. Identify every deferred derivation, access/module and historical verification obligation.
2. Bind a compact private result to the exact ClassId, registry metadata and verification environment. Process all declared methods in file order using the existing checker. Define whether individual decoded bodies are released as each method completes and which aggregate counts and diagnostics the caller needs. The expected result is evidence of complete modern class type checking in this environment. Define separate future requirements for using it to authorize execution. In particular, equal registry IDs alone cannot demonstrate that two independently supplied loading environments have the same initiating-loader bindings.
3. Bound the entire class. A per-method ceiling permits work multiplied by method count. Pin aggregate decoded bytes, declarations, metadata, type/cache records, cells, edges, UTF-16 and work, with checked inclusive accounting, a deterministic first failing declaration, and enough completed usage to diagnose late failure. Reuse method rules and explicit resource funding. Cache ownership and fallible allocation need clear bounds. Host policy exhaustion and unavailable facts may be retried with sufficient resources or different facts. A future linking lifecycle must specify when a Java LinkageError becomes sticky across verification attempts. [JVMS 5.4.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.1).
4. Require new independent evidence. Include empty modern classes, interfaces, designated Object, a shared valid first method followed by an invalid unused method, a bodyless final override, missing facts reached only in a later method, mixed wide/constructor/handler bodies and many tiny methods under a class allowance. Compare genuine class totals with the accepted individual-method corpus and test method count, exact aggregate limits, deterministic failure location and absence of partial results. JDK tooling should distinguish whole-class definition/verification failures from later invocation errors.

The following work belongs in subsequent contracts: historical data-flow inference and the version-50 policy, cross-loader loading constraints during preparation and resolution, class lifecycle failure records, and an opt-in execution path that consumes evidence under compatible bindings. Loading-constraint planning must include signature element types across overriding superclass/superinterface declarations, selected inherited methods and constraint checks when a loader later obtains a definition. These distinctions matter for a JVM that must verify a class before use and report the correct failure stage. [JVMS 5.3.4](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.3.4) and [JVMS 5.4.2](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.2).
